# Build the Django backend for AJ Jeweler

You are building the server for an existing Flutter app that runs a two-branch
gold shop in the Philippines (Kidapawan and Davao). The app is finished and in
use on a phone; it currently keeps everything in memory and saves one JSON file
to the device. Your job is the database schema and the HTTP API it will talk to.
Do not design new features — match what the app already does.

**Stack:** Django 5 + Django REST Framework + PostgreSQL. Media (photos, receipt
PDFs) on local disk in development, S3-compatible storage in production.

---

## Non-negotiable rules

These come from how the shop actually works. Enforce them in the service layer
and in the database where possible, not only in the client.

1. **Money is integer centavos.** Never floats. `₱1,037,903.00` is `103790300`.
   Weights are grams with 3 decimals (`DecimalField(max_digits=10,
   decimal_places=3)`).
2. **Balances are derived, never stored.** A branch's cash balance is its
   opening balance plus every signed cash-ledger entry for that branch and cash
   account. There must be no "current balance" column anywhere. Expose balances
   as computed values.
3. **Three separate pots of money per branch** (`purchase`, `sales`, `bank`):
   - Paying a customer for a purchase comes **out of `purchase`**.
   - The cash part of a sale goes **into `sales`**; the bank-transfer part goes
     **into `bank`**. Sale takings never top up the purchase float.
   - Loan proceeds go **into `purchase`**.
   - Moving money between pots (or branches) is a transfer: two matched rows.
4. **Records are never silently deleted.** Corrections are new rows plus a log
   entry holding before/after values. The only hard deletes are: a cash entry
   typed by hand, a partition drawn by mistake, and a user who has no records.
5. **Every write names a person.** Each mutating request records the acting
   user, and writes an append-only `TransactionLog` row.
6. **IDs are 6-character codes** generated by the client: alphabet
   `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (no 0/O/1/I), e.g. `A7K2M9`. They are
   unique across **all** record types — one code identifies exactly one record.
   Accept the client's id as the primary key; reject duplicates with 409.
   User ids look like `USR-AJ01` or `USR-<6 chars>`.

## Schema

### Branch
`id` (`kidapawan`/`davao`, PK), `starting_purchase_cash_centavos` int,
`starting_sales_cash_centavos` int, `starting_bank_centavos` int.
Exactly two rows. Opening balances are the only stored money figures.

### User
`id` (PK, string), `name` (unique, case/whitespace-insensitive), `role`,
`home_branch` (null only for `admin`; required for every other role),
`contact_number` (nullable), `active` (default true), `created_at`.

Rules: at least one **active admin** must always exist — block demoting,
deactivating or deleting the last one. A user may only be hard-deleted when no
record references them; otherwise deactivate. Deactivated users keep appearing
on their past records.

### Customer
`id` (PK), `name`, `contact_number` (null), `address` (null), `first_seen`,
`photo` (image, null).

Matching: normalise the name (trim, collapse whitespace, lowercase) to decide
whether an incoming transaction belongs to an existing customer. **Never blank
an existing detail** — a transaction that omits the address must not erase the
address captured last month, but supplied details do overwrite.

Transactions also store a **snapshot** of the customer (`name`,
`contact_number`, `address`, `customer_id`) so an old receipt keeps saying what
it said on the day. The photo is *not* snapshotted — screens always show the
customer's current photo.

### PurchaseBatch
One customer visit. `id` (PK), `customer_snapshot` (embedded fields above),
`customer` FK (null), `branch`, `date`, `submitted_by_role`,
`verification_status`, `verification_note` (null), `released_at` (null),
`submitted_by` FK user (null), `released_by` FK user (null),
`release_proof_photo` (image, null).

### Item
A piece of metal. `id` (PK), `description`, `weight_grams` (**net**),
`gross_weight_grams` (null for partitions), `karat` (int: gold ≤ 24, silver
fineness ≥ 100 such as 925/999), `type`, `capital_amount_centavos`, `origin`
(customer name as typed), `branch`, `item_status`, `verification_status`,
`purchase_date`, `submitted_by_role`, `photo` (image, null), `encoded_by` FK
user (null), `batch` FK (null), `verification_note` (null),
`parent_lot` FK self (null), `original_grams`, `original_amount_centavos`,
`remaining_grams`, `remaining_amount_centavos` (all four null until the lot is
first partitioned).

Rules:
- **Purity must match the metal**: `silver` items carry a silver fineness
  (≥100); `goods`/`scrap` carry a gold karat (≤24). Reject mismatches.
- On verification: `scrap` → `forDisposal`; `goods` and `silver` → `listed`.
- A **partition** draws grams and amount out of a parent lot, inherits the
  lot's karat and metal, and reduces the lot's remaining figures. It can never
  draw more than remains. Deleting a partition gives both back.
- Changing a lot's karat cascades to its partitions. A lot that already has
  partitions cannot change metal. Sold and disposed items cannot be edited.

### Sale
`id` (PK), `customer_snapshot` + `customer` FK, `note` (null),
`cash_centavos`, `bank_centavos`, `verification_status`,
`verification_note` (null), `branch`, `date`, `submitted_by_role`,
`submitted_by` FK, `received_by` FK.

### SaleLineItem
`sale` FK, `item` FK, `negotiated_price_centavos`, `final_grams` (null → use
the item's net weight). Store an item snapshot too, so a completed sale still
prints what was sold even if the item is later corrected.

### Commitment
A cash loan repaid in scrap gold. `id` (PK), `lender`,
`amount_centavos`, `rate_per_gram_centavos`, `branch` (**null = company-wide**),
`date_approved`, `date_received` (null until cash arrives),
`received_proof_photo` (image, null).

Balance, amount repaid and status (`loanPending` → `loanReceived` → `loanPaid`)
are **derived** from the disposal batches applied to it — never stored, never a
button someone presses.

### DisposalBatch
Scrap or silver sold off to settle a loan. `id` (PK), `branch`, `item_ids`
(M2M to Item), `capital_centavos`, `gross_grams`, `gross_amount_centavos`,
`commitment` FK (**required**), `date`, `photo` (image, null).

Completing a batch marks every item `disposed`. It moves **no cash** — the
gross pays down the commitment.

### CashEntry
The one place money moves. `id` (PK), `branch`, `type`, `account`,
`amount_centavos` (always positive), `note` (required), `category` (expenses
only), `date`, `recorded_by_role`, `recorded_by` FK, `source_type`,
`linked_record_id` (the purchase/sale/commitment, null for manual),
`transfer_pair_id` (shared by both halves of a transfer).

Rules: entries with `source_type != manual` are **read-only** — correct the
source record instead. A transfer is always two rows sharing a pair id, edited
and deleted together, and must move between different branch/account
combinations.

### GoldRate and RateChange
`GoldRate`: `karat` (PK, gold ≤24 or silver ≥100), `price_per_gram_centavos`,
`updated_at`. One row per purity — adding a duplicate is an error.

`RateChange`: `karat`, `before_centavos` (null when first set),
`after_centavos`, `at`, `user` FK, `restored_from` (null, or the date whose
prices were re-applied). Never deleted; it is the price history.

### StoredReceipt
`id` (PK), `record_id` (purchase or sale), `kind`, `branch`, `counterparty`,
`total_centavos`, `issued_at`, `pdf` (file), `text` (plain-text version).
One current receipt per record — re-issuing replaces it.

### TransactionLog
Append-only. `id` (PK), `at`, `action`, `user` FK (null), `user_name`
(denormalised so the log survives), `role`, `summary`, `branch` (null =
company-wide), `record_id` (null), `record_kind` (null), `amount_centavos`
(null), `changes` (JSON list of `{field, before, after}` strings).

Never update or delete a log row.

## API

REST under `/api/v1/`, JSON, DRF. Authentication: token or JWT; every request
is made as a staff user, and the server takes the actor from the token (do not
trust a client-supplied actor id). Permissions follow the roles:

| Capability | Roles |
| --- | --- |
| Encode purchases | assistantAppraiser, admin |
| Build sales | salesRep, admin |
| Verify, release and receive cash | cashier, admin |
| Disposal, commitments, rates, corrections, user management | admin |
| Read lists and records | all roles |

Branch staff see their own branch; admin sees both (`?branch=` omitted).

### Conventions
- Amounts in centavos as integers, weights as strings with 3 decimals, dates
  ISO-8601, enums by name.
- Every list endpoint supports `?branch=`, `?from=`, `?to=`, `?q=`, and
  pagination.
- Refusals that are business rules (not bugs) return **422** with
  `{"error": {"code": "...", "message": "..."}}`, where the message is the
  plain-English sentence the app shows, e.g.
  *"A silver piece needs a silver purity (e.g. 925), not a gold karat"*.
- Writes accept an `Idempotency-Key` header; replaying a key returns the first
  result instead of acting twice.

### Endpoints

**Session and staff**
- `POST /auth/login`, `POST /auth/refresh`, `GET /me`
- `GET/POST /users`, `GET/PATCH /users/{id}`
- `POST /users/{id}/deactivate`, `POST /users/{id}/reactivate`
- `DELETE /users/{id}` → 422 when they appear on any record, with the count

**Reference**
- `GET /branches` → both branches with the three balances and today's money in
  and out per account
- `GET /rates` (gold and silver), `POST /rates` (add a purity),
  `PATCH /rates/{karat}`
- `GET /rates/history?karat=&from=&to=`
- `GET /rates/on/{date}` → every purity's price at the close of that day
- `POST /rates/apply` `{date, silver: bool}` → re-applies that day's whole
  table for one metal, one new history row per changed rate

**Customers**
- `GET /customers?q=`, `GET /customers/{id}` (with their purchases and sales)
- `POST /customers`, `PATCH /customers/{id}`, `PUT /customers/{id}/photo`

**Purchases**
- `POST /purchases` — one customer visit with many lines (description, gross
  and net grams, karat, type, amount, optional photo). Creates the batch and
  its items as `awaitingVerification`. **No cash moves.**
- `GET /purchases`, `GET /purchases/{id}`
- `POST /purchases/{id}/release` — multipart with the **required proof photo**.
  Verifies every item, routes each to `listed`/`forDisposal`, writes **one**
  cash entry against `purchase` cash, stamps who released it.
- `POST /purchases/{id}/return` `{note}` — sends it back to the encoder
- `PATCH /items/{id}` — admin correction (description, type, karat, weights,
  amount). Returns the list of field changes. **Never moves cash**, even on a
  paid purchase: say so in the response.
- `PUT /items/{id}/photo`
- `POST /items/{id}/partitions` `{description, type, grams, amount, photo?}`
- `DELETE /partitions/{id}` — returns grams and amount to the lot

**Sales**
- `GET /items/sellable?branch=&silver=` — verified, listed, not scrap
- `POST /sales` — checkout: line items with negotiated price and final grams,
  customer, intended payment. Items become `reserved`. **No cash moves.**
- `GET /sales`, `GET /sales/{id}`
- `POST /sales/{id}/complete` `{cash_centavos, bank_centavos}` — must total the
  sale. Marks items `sold`, writes a `sales` cash entry and/or a `bank` entry.
- `POST /sales/{id}/return` `{note}`, `POST /sales/{id}/resubmit`
- `POST /items/{id}/release-reservation` — abandoned cart

**Disposal**
- `GET /disposal/pool?branch=&silver=` — gold scrap awaiting disposal, or
  silver stock on hand
- `POST /disposal` `{branch, item_ids, capital, gross_grams, gross_amount,
  commitment_id, date, photo?}`
- `GET /disposal`, `GET /disposal/{id}` (with the karat breakdown: grams per
  purity, highest first)

**Commitments**
- `GET /commitments` (each with derived balance, repaid amount and status),
  `GET /commitments/{id}`, `POST /commitments`
- `POST /commitments/{id}/receive` — multipart with the **required proof
  photo**; writes a cash entry into that branch's `purchase` cash (company-wide
  loans credit no branch)

**Cash**
- `GET /cash/entries?branch=&account=&type=&from=&to=`
- `GET /cash/balances?branch=` — per account: opening, current, today in/out
- `POST /cash/entries` — manual cash in / expense / withdrawal, with account
- `POST /cash/transfers` `{from_branch, from_account, to_branch, to_account,
  amount, note, date}` — writes the matched pair
- `PATCH /cash/entries/{id}`, `DELETE /cash/entries/{id}` `{reason}` — manual
  entries only; 422 on linked ones, explaining where to correct it

**Receipts, logs, exports**
- `POST /receipts` `{record_id, kind}` → generates and stores the PDF plus the
  plain-text version; `GET /receipts`, `GET /receipts/{id}` (and the file)
- `GET /logs?branch=&category=&user=&from=&to=&q=`, `GET /logs/{id}`
- `GET /exports/{purchases|sales|expenses|withdrawals}?format=csv|xlsx|pdf`
  — the app can build these itself; server-side is a convenience, same columns

## Migrating what already exists

The phone holds the live data as one JSON file written by
`mobile/lib/core/data/snapshot_codec.dart`; read that file for the exact field
names and shapes. Provide `POST /sync/import` that accepts one of those
snapshots and creates every record with its existing ids, so the shop's current
data moves to the server without re-entry. Importing twice must not duplicate
anything.

## Acceptance

The app's own test suite (179 tests in `mobile/test/`) encodes the rules above —
read it as the specification it is. At minimum, prove with Django tests:

1. A purchase moves no cash until release; releasing writes exactly one cash
   entry for the whole batch, against `purchase` cash.
2. A split sale payment puts the cash half in `sales` and the bank half in
   `bank`, and leaves `purchase` untouched.
3. Each branch's three balances equal opening + its own entries, always.
4. A partition never draws more than its lot has left, and deleting it restores
   the lot exactly.
5. Disposal marks items disposed, moves no cash, and draws down its commitment;
   the commitment flips to paid on its own when the balance reaches zero.
6. Silver with a gold karat (or the reverse) is refused.
7. A linked cash entry cannot be edited or deleted; a manual one can, and both
   halves of a transfer move together.
8. The last active admin cannot be demoted, deactivated or deleted.
9. Every mutation writes exactly one log row naming the actor, and corrections
   carry before/after values.
